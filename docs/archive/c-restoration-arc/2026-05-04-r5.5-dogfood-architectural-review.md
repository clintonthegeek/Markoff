# R5.5 Dogfood — Architectural Review

> **This is not a fix proposal.** This document captures what the R5.5
> dogfood iteration revealed about the live-render architecture and the
> documents that govern it. It enumerates open questions that must be
> answered before the next significant code change. Five candidate doc
> amendments are listed at the end; none are pre-approved.
>
> **Do not start a new fix iteration from this document.** The recommended
> next step is to read it, decide on the architectural questions, and
> *then* re-plan R5.5 (or its replacement) from the answers.

**Status:** R5.5 implementation is in a state where mid-block split typing
works, hole creation works, but multiple architectural-level issues
surfaced in user dogfood that one-bug-at-a-time fixes cannot resolve. The
fixes that did land during the iteration (commits TBD on this branch) are
correct in isolation but each one exposed the next bug in the layer
beneath it — the v0 cycle-guard pattern recurring under different names.

**Read also:** `docs/handoff/2026-05-03-r5-holes-postmortem.md` (which
this document partially supersedes — the v2 design's premises that
appeared sound at design time are revisited here against dogfood evidence).

---

## 1. What we observed (in surface order)

Each entry below pairs a user-visible failure with the code-level diagnosis
that emerged from `[dogfood]` log instrumentation. The fixes shipped on
this branch are noted; the architectural revelation each fix exposed is
the load-bearing part of this section.

### 1.1 Bug A — proxy `beginResetModel` on every structural edit

**Symptom (user):** *"the caret disappears and the whole view scrolls to the top of the page"* on mid-paragraph Enter.

**Diagnosis:** `LiveProxyBlockModel::onInnerRowsInserted` and `onHoleInserted` both called `rebuildMapping()`, which is `beginResetModel/endResetModel`. A QML `ListView` model reset destroys every realised delegate (including the focused TextEdit) and snaps `contentY` toward 0.

**Fix shipped:** targeted `beginInsertRows/endInsertRows` for both paths.

**What this exposed:** v2 spec §4.3 *correctly* specified targeted insert. The implementation diverged because of an apparent `Qt.labs.qmlmodels DelegateChooser` quirk discovered during R5.5 Task 17. The quirk's *true* root cause was a different bug (`KindRole` returned empty for hole rows, fixed at `data()` level), but the workaround for the symptom (full reset) outlived the underlying fix and was never escalated to a spec amendment. **The amendment process broke silently.**

### 1.2 Bug B — `requestTextCaretAtRow` conflated two semantics

**Symptom (user):** *"the caret jumps to the start of the first line of the following paragraph"* on mid-block Enter.

**Diagnosis:** `requestTextCaretAtRow(row, qtPos)` had a "resolve immediately if `row < signalModel.rowCount()` else wait for `rowsInserted`" gate. For mid-block split, the target row index already exists (it's the *next* paragraph after the one being split). The gate resolved immediately to that paragraph's anchor, then the parse arrived and inserted a new row at the same index, leaving the cursor pinned to the *shifted* old block.

**Fix shipped:** added `requestTextCaretAtNewRow(row, qtPos)` — pure-pending, never resolves immediately. Mid-block split uses the new method.

**What this exposed:** the API conflated two different operations under one name. Backspace-merge needs "row already exists, just move cursor"; mid-block split needs "row will be born here, wait for it." The conflation was hidden because pre-fix Bug A's model reset destroyed the wrongly-targeted delegate, so the misplaced cursor was invisible.

### 1.3 Bug C — `holeReified` cursor delivery never wired

**Symptom (user, post Bug-A fix):** *"the first letter appears, then the caret disappears and input is unresponsive"* on typing into a hole that committed via idle.

**Diagnosis:** v2 spec §5.3 line 396 stated "LiveCursorState, listening to `holeReified`, schedules `requestTextCaretAtRow(proxyRowForAnchor(newRowAnchor), bufferText.length())`." This was specified and **never implemented**. After idle-commit fired, the hole was abandoned, the new paragraph appeared, but no cursor was scheduled to land on it.

**Fix shipped:** `LiveHoleLayer::aboutToCommit(holeId)` signal emitted before the hole row vanishes. `LiveListModelBinding` listens, captures `proxyRowForHole(holeId)` and `bufferText.length()`, calls `requestTextCaretAtNewRow(proxyRow, bufferLen)`. `LiveCursorState::request` was also amended to `m_pendingRow.reset()` so an explicit request supersedes a stale pending.

**What this exposed:** the spec used the verb `routeFocusIn` (§5.3 line 396) without ever defining its signature, contract, or call site. The post-mortem's claim that "focus delivery is one primitive" (line 257) treated cursor *state* and QML focus *delivery* as the same thing — they aren't. Every downstream document inherited this elision.

### 1.4 Bug D — `BlockAnchor` instability under in-place edits at qtPos 0

**Symptom (user, post Bug-C fix):** typing the first character into the new paragraph from a mid-block split worked, but the cursor disappeared after that one character.

**Diagnosis:** `BlockAnchorComputation.cpp:35` computes each block's `BlockAnchor` as `doc.textAnchorAt(startByte, leftBias=true)`. The CRDT `TextAnchor` identity ties to a specific character. When the user inserts at `qtPos=0` of the block, that character is now the just-typed one — anchor identity changes. `AstBlockDiff` keys on `{kind, anchor}`, sees prev[N] ≠ next[N], emits `Delete[N,N] + Insert[N,N]`. The QML delegate is destroyed and recreated; the focused TextEdit is destroyed; `LiveCursorState`'s TextCaret pins to a now-dead anchor; `Component.onCompleted` on the new delegate sees no match.

**Fix shipped (workaround):** `AstBlockDiff::diff` post-pass collapses adjacent same-position-same-kind `Delete+Insert` pairs into `Equal+renumber`. `LiveBlockModel::applyOps` for collapsed Equal emits `anchorRenumbered(row, oldAnchor, newAnchor)`. `LiveCursorState` listens and silently swaps its TextCaret's anchor in place — no `cursorChanged` emit, so the QML delegate is unaffected and the user's TextEdit cursor position is preserved.

**What this exposed:** the architecture's identity model — "block = stable BlockAnchor across parses" — is not actually held by the foundation. The foundation gives block anchors stable *under bytes-after-the-anchor change*, but unstable *under bytes-at-the-anchor change*. Live-render assumed the stronger guarantee everywhere and built cursor identity, diff identity, and renumber semantics on it. The workaround hides the foundation's behaviour from the live-render layer; it could mask a real same-position-same-kind structural change (rare but possible) by misclassifying it as a renumber. **This is not a foundation-level fix.**

### 1.5 Bug E — byte arithmetic at end-of-block inserts into the separator

**Symptom (user):** typing at the end of a paragraph (or click-in-gap that hit-tested to end-of-paragraph) caused each character to *eat one paragraph separator*, walking the cursor down the document and merging paragraphs as it went.

**Diagnosis:** tree-sitter's CommonMark grammar includes the trailing `\n` of each paragraph in that block's `byteEnd` range. `BlockWalker` faithfully extracted this — `rec.text` for a paragraph "hello" was `"hello\n"` (6 chars). `editLen=6` in the QML TextEdit. User clicks at end → `qtPos=6`. User types `"y"` → `LiveEditBinding.applyLocalEdit` at byte `blockStart + 6`. But `blockStart + 6` is the position of the **second** `\n` of the `\n\n` separator. The new char inserts between the two `\n`s, turning `"hello\n\nworld"` into `"hello\nyworld"` — one paragraph with a soft break, eating the next paragraph. Each subsequent keystroke eats the next separator.

**Fix shipped:** `BlockWalker` trims one trailing `\n` from `rec.text`. The visible content matches the source's content-byte count. End-of-block insertions now land at the correct byte (first `\n` of separator).

**What this exposed:** an existing test (`tst_live_render_structural.cpp:239`) explicitly *asserted* the buggy behaviour with the comment *"Parser includes the paragraph-separator \n in the first block's byte range"* — the bug was encoded as a contract. End-of-block insertion in a multi-paragraph document had **never been tested**. All paragraph-edit tests used single-paragraph fixtures (`"hello"`) where end-of-block has no separator to land in.

### 1.6 Bug F — EOB-Enter UX is the wrong abstraction

**Symptom (user):** *"pressing enter at the end of a paragraph should create a new paragraph, not lead to prepending text to the start of the following paragraph."*

**Diagnosis:** not a bug — it's the v2 hole design as specified. Pressing Enter at end of a paragraph creates a `LiveHoleLayer` hole. The hole has its own buffer, idle-commit timer, IME guard, per-hole undo stack, focus-routing semantics, abandon paths, and reify protocol. From the user's mental model, it's a non-obvious indirection: they pressed Enter, they expected a new paragraph, instead they got a phantom row with subtle commit semantics. From a code perspective, it's a separate authority over text content (the `bufferText` that lives outside the CRDT until commit), with all the cycle-guard surface area that entails.

**No fix shipped — this is the central architectural question of §3.1 below.**

### 1.7 Latent — async commit window race

**Not directly observed in user dogfood but structurally present.** Between idle-commit firing and parse-back arrival (~30–100 ms), the hole row has been removed but the new paragraph hasn't appeared. If the user types during this window, focus is wherever Qt put it (probably the next sibling delegate or ListView root). The post-mortem (`r5-holes-postmortem.md` line 108) claimed v1 design eliminated this: *"there are no intermediate keystrokes during a quiescent commit by definition."* The claim is wrong for slow human typing — a 250 ms idle is not "quiescence", it's "the user is thinking." The post-mortem's quiescence definition assumed a typing pattern that doesn't match dogfood reality.

## 2. The pattern

Six bugs, six fixes, each one exposing the next. Three layers of cover were
hiding the three deepest issues:

| Cover | Was hiding |
|---|---|
| Bug A (proxy `beginResetModel`) destroyed all delegates → focus loss looked like "reset" | Bugs B (cursor mistargeting), C (no holeReified delivery), D (anchor instability) — all three were silent because focus was already gone |
| Bug B (immediate-resolve in `requestTextCaretAtRow`) sent cursor to wrong block → looked correct because the wrong block's delegate was destroyed by Bug A anyway | Bug D (anchor change destroys the *correct* target delegate too, but at a different time) |
| Bug E (encoded as a test assertion) was hidden by single-paragraph test fixtures — no separator to land in | Bugs in any path that does end-of-block byte arithmetic on a multi-paragraph doc |

The post-mortem (`r5-holes-postmortem.md` §6) named this pattern explicitly:
> "Pairwise reconciliation, not global. Each cycle guard was scoped to one specific seam. None knew about the others. ... Holes added another seam, which would have been another exception, which would have produced another structural-handler-level workaround."

The v2 design retired the *original* cycle guards (`m_applyingModelUpdate`, `m_applyingModelBuffer`, `m_composing`, `if (textEdit.activeFocus) return`, `m_applyingSessionSelection`, the local TextEdit truncation hack). It introduced a new set: the proxy's reset-as-workaround, the cursor API's conflated semantics, the anchor-collapse-and-renumber pattern, the trailing-`\n` trim. **Each is a cycle guard for an architectural mismatch the v2 design didn't anticipate.** This is the pattern recurring, not the pattern resolved.

The systematic-debugging skill's "if 3+ fixes failed, question the architecture" criterion is met three times over within a single dogfood iteration. Continuing to iterate fixes without an architectural reset is uneconomic — the rate of new bug-discovery is matching the rate of bug-fix.

## 3. Open architectural questions

These must be answered before the next significant code change. Each
section frames the question, lists candidate answers, and gives a
recommendation flagged as such. **None of these are decisions yet.**

### 3.1 What is a hole, structurally?

The hole exists because tree-sitter's CommonMark grammar emits zero block nodes for blank-only regions of source. EOB-Enter inserts `\n\n` at the end of paragraph X; the parser sees `paragraph_X_content\n\n` followed by EOF (or another block); no parser block exists for the cursor to land in. The hole is the live-render layer's invented "row that should exist but the parser can't represent yet."

Four candidates for what the hole *is*:

**(a) Keep current v2 (LiveHoleLayer + LiveProxyBlockModel + idle-commit + buffer-mirror + per-hole undo).** Multiple authorities over content; complex commit semantics; idle-commit race; UX surprise per Bug F. Status quo.

**(b) Simplify v2: drop idle-commit, drop per-hole undo, keep buffer-mirror + commit-on-focus-out / save / explicit-Enter.** Resolves the async-window race (1.7) and the per-hole-undo complexity. Still two authorities over content (CRDT + bufferText). Still an "indirection" the user experiences.

**(c) Parser-side workaround: insert a zero-width or invisible marker character so the parser produces a block.** EOB-Enter does `applyLocalEdit("\n\n​")` (zero-width space) instead of `"\n\n"`. Parser produces a paragraph containing `​`. View renders it as empty. Cursor lands on it normally via the existing parser-driven row path. First user keystroke replaces the marker. **Single source of truth (CRDT); no LiveHoleLayer; no LiveProxyBlockModel; no buffer-mirror; no idle-commit; no holeReified cursor delivery; no aboutToCommit signal.** All of bugs C and D's workarounds become unnecessary. Risk: marker character persists in saved file if the user moves away without typing — needs an "abandon-marker-on-focus-out-with-no-typing" path. Risk: zero-width chars are user-confusable.

**(d) Atomic phantom: view-side row inserted at the proxy level only. Each keystroke writes through to `applyLocalEdit` immediately at the phantom's anchored position.** The phantom is an empty *editable surface* over the CRDT, not a separate buffer. As soon as the parser produces a real block at that position, the phantom is replaced atomically. No commit, no abandon, no idle, no per-hole undo (the regular CRDT undo applies). The tricky part: each keystroke writes to a position that doesn't yet have a parser block, so byte-position arithmetic must use the phantom's reify-anchor directly.

**Recommendation:** (c) deserves serious investigation. It's the smallest possible architectural surface that solves the original "EOB-Enter has nowhere to put the cursor" problem. It also collapses a large fraction of the v2 implementation into "one applyLocalEdit and a parser-driven row." If the marker-leakage risk can be addressed (focus-out-no-typing → undo the marker; pre-save scrub of `​` chars; visible warning if user types `​` themselves), this is dramatically simpler than (a) or (b). Worth a short spike to verify tree-sitter accepts `​` as paragraph content. (d) is more elegant in theory but requires inventing a "row that exists in the proxy but not the parser" state, with all its synchronisation semantics — basically v2 minus idle-commit, which is (b).

### 3.2 BlockAnchor stability — foundation amendment?

Bug D's workaround (collapse Delete+Insert at same position+kind) is a live-render-layer band-aid for a foundation-level guarantee that doesn't hold. The right architectural fix is in the foundation.

**(a) Status quo + workaround:** `BlockAnchor = textAnchorAt(startByte, leftBias)`. Live-render handles the renumber via the `anchorRenumbered` signal. Risk: the workaround mis-classifies real same-position-same-kind structural changes as renumbers. Acceptable for typing, possibly broken for esoteric structural edits.

**(b) Foundation amendment: stable opaque block IDs.** Each top-level block gets a CRDT-stable opaque ID on first appearance. Persists across parses for blocks that are "the same block" (heuristic — first-byte content + length? incremental tree-sitter node identity?). `BlockAnchor` becomes `{stableId, firstByteAnchor}`; identity uses `stableId`. Significant foundation work.

**(c) Foundation amendment: anchor at block interior, not boundary.** `BlockAnchor` anchors at byte `startByte + N` for some interior offset N. Inserts at `qtPos < N` would still shift identity, but inserts at `qtPos >= N` wouldn't. Heuristic; doesn't fully solve.

**(d) Foundation amendment: switch to `rightBias` + interior anchor.** A different bias choice may produce different stability properties. Needs CRDT-engine analysis (collabtext semantics).

**Recommendation:** (b) is the right architectural answer. (a) is acceptable as a holding pattern *if* §3.1 picks (c), because the marker-character approach reduces the surface area where anchor instability bites. Defer (b) until after §3.1 is decided — it may become unnecessary.

### 3.3 Block byte-range conventions

Tree-sitter's `tlb.byteEnd` for a paragraph includes the trailing `\n`. `BlockWalker` (post-fix) trims it from `rec.text`. `BlockAnchorComputation.endByte` does *not* trim — it reflects tree-sitter's range. So `rec.text.size() != blockEnd - blockStart`. Discrepancy matters for any code that crosses the rec.text vs. byteRange boundary.

**(a) Trim everywhere.** `BlockAnchorComputation.endByte` also subtracts trailing `\n`. Single semantics: "block range = visible content bytes." Add a regression test asserting `rec.text.size() == blockByteRange().endByte - blockByteRange().startByte` for all blocks.

**(b) Don't trim anywhere (revert Bug E fix).** Reverts to the pre-fix end-of-block typing breakage. Rejected.

**(c) Status quo: `rec.text` trimmed, `endByte` not.** Discrepancy lives. Comment in spec/code documents which one to use for what. Risky — easy to grab the wrong one.

**Recommendation:** (a). The discrepancy in (c) is exactly the kind of pinhole defect that'll bite a fresh agent six months from now. Pin one convention, write the regression test.

### 3.4 Async commit window race (1.7)

If §3.1 picks (c) marker-character, this question is moot — there is no commit, no parse-back window, no race.

If §3.1 picks (a) or (b) v2-with-or-without-idle-commit, the race must be addressed:

**(a) Suppress idle-commit while hole has focus.** Commit only on focus-out, save, or explicit Enter. Quiescence-as-time-since-last-keystroke was the wrong signal; "user moved focus away" is the right signal. Diverges from v2 spec; needs amendment.

**(b) Buffer keystrokes during the in-flight commit window.** Apply them once parse arrives. Adds a queue layer in `LiveEditBinding`; complexity.

**(c) Remove idle-commit entirely.** Same as (a), more aggressive.

**Recommendation:** moot pending §3.1. If §3.1 picks v2-style, then (a). The post-mortem's "quiescence" assumption was empirically wrong; commit on intent-signal, not time-elapsed.

### 3.5 Test-fixture taxonomy

Every paragraph-edit test in the live-render suite uses a fixture like `"hello"` or `"para1\n\npara2"`. None exercise:

- **LLM-wrapped paragraphs:** ~250 char paragraphs with internal soft-break `\n`s.
- **Human-long-line paragraphs:** ~1500–3000 char single-line paragraphs.
- **Mixed structure:** headings, paragraphs of varying length, code blocks, HRs interleaved.
- **Long-doc scroll:** documents with > 100 blocks, where mid-block edits happen on rows that are *not* the only visible row.

Bugs E (end-of-block byte arithmetic) and the slow-typing race (1.7) are both invisible at the small-fixture scale.

**Recommendation:** add a test base class `WithFixture` parameterising every paragraph-edit and structural test over: short-snippet, llm-wrapped, human-long-line, multi-block-mixed, hundred-block-scroll. The spec's §10.3 dogfood scripts should also explicitly require all fixture variants. **Make this a contract on every test added going forward, not a retroactive sweep.**

### 3.6 Process: amendment-discipline trip-wire

The proxy's `beginResetModel` workaround (Bug A) was applied silently. The amendment process exists (`docs/restoration-status.md` §"Spec-amendment log") but no mechanism enforces its use when the implementation diverges from the spec.

**Recommendation:** add a checklist item to commit messages or PR descriptions that touch `*.cpp` files mentioned in the spec's signal-shape sections: *"Did this commit change a signal shape, an op semantics, a model contract, or a public API? If yes, link the amendment entry."* Failing the check requires either an amendment proposal or an explicit "no, this preserves the contract" justification.

### 3.7 Process: post-mortems as test specifications

The R5-holes post-mortem identified F2 (character scramble during fast typing) as v0's worst failure. The R5.5 implementation was *gated* against F2 by a synthetic broken stub. But it was *not* gated against F2 recurring under a *different trigger* (idle-commit between human pauses, instead of reify-on-first-keystroke). The post-mortem's claim that v1 design "structurally eliminated" the race was treated as narrative; it should have been treated as a *test specification* requiring regression coverage on the hardest realistic case.

**Recommendation:** every post-mortem must include a "Failure-mode regression test inventory" section enumerating: each historical failure mode, the test fixture proving it can't recur, and the *trigger conditions* the test exercises. A failure mode without a regression test on a real-shape fixture is not "fixed"; it's "currently asleep."

## 4. What the post-mortem said and what we missed

The R5-holes post-mortem (`r5-holes-postmortem.md`) was a careful, well-structured document. Re-reading it against the dogfood evidence reveals **specific lines whose claims didn't survive contact with reality.** This section catalogues them so future post-mortems can be calibrated.

| Post-mortem claim | Dogfood reality | What we should have done |
|---|---|---|
| §3 line 257: "focus delivery is one primitive, `LiveCursorState::requestTextCaretAtRow`" | `requestTextCaretAtRow` sets cursor *state*; QML focus delivery to a TextEdit is a separate operation entirely. The "one primitive" framing hid a missing implementation. | Demanded a concrete contract for *who calls* `forceActiveFocus()`, *when*, *against what model state*. The spec used the verb `routeFocusIn` without ever defining it. |
| §3 line 270 (open question): "The proxy's behaviour during `LiveBlockModel::modelReset` ... are pending holes preserved across a reset?" | The question only considered the *file-load* model-reset path. It didn't ask whether the proxy *itself* would issue `beginResetModel` during normal editing — which it did (Bug A). | Asked the dual question: "does the proxy ever emit modelReset during in-place edits, and if so, what guarantees does the live-render layer make that delegates and focus survive?" |
| §F2 line 108: "v1 ... structurally absent: there are no intermediate keystrokes during a quiescent commit by definition" | "Quiescent" was defined as "≥ 250 ms since last keystroke." A human dogfooder pauses ≥ 250 ms between characters routinely — every pause triggers a commit. The race is fired *constantly* in dogfood, just at a different trigger. | Defined "quiescent" empirically: instrument an actual user typing a paragraph; measure the distribution of inter-keystroke gaps; pick the idle threshold from the data. |
| §6 lines 89–91 ("v0 vs. v1 axes"): the table claimed v1 reduced "Sources of truth" from six to five | v2 implementation (which the post-mortem describes) added: the proxy's m_rows mapping, the cursor's stale-anchor recovery, the renumber-anchor, the hole's bufferText. Net authorities: roughly the same as v0, just renamed and reorganised. | Counted authorities at the API boundary, not at the conceptual level. |
| §A1 spec amendment: "v0 implementation permanently retired; v2 is structurally distinct" | The phrase "structurally distinct" was used to justify treating v0's failure modes as inapplicable. But the *trigger conditions* are different while the *failure modes* (focus race, character scramble, cursor on wrong row) are the same. | Mapped each v0 failure mode to a "trigger-conditions changed?" check; required regression tests for each, not just narrative dismissal. |

**Meta-observation:** the post-mortem was strongest where it diagnosed the *audit's* findings (six sources of truth, cycle-guard pile, retry-loop pile). It was weakest where it *claimed* the v2 design eliminated those issues — those claims were structural assertions, not test results. Future post-mortems should treat any "v_next eliminates failure mode X" claim as requiring a falsifiable regression test against a realistic fixture *before* the claim ships in the doc.

## 6. Specific recommendation

**Stop the R5.5 implementation iteration.** Do not write more fixes against
the current architecture. Instead:

1. **Decide §3.1 (what is a hole) first.** This is the load-bearing
   architectural decision. The recommended path is a short spike on §3.1(c)
   — try the marker-character approach in a throwaway branch, verify
   tree-sitter accepts `​` as paragraph content, write a one-paragraph
   end-to-end test (EOB-Enter → marker hole appears → first keystroke
   replaces marker → idle commits not needed). If the spike works, §3.1(c)
   collapses most of the R5.5 implementation surface. If it doesn't, fall
   back to (b) simplified-v2.

2. **Decide §3.3 (byte-range conventions).** Pin one convention,
   write the regression test. This is independent of §3.1 and can land in
   parallel.

3. **Decide §3.5 (test-fixture taxonomy) and §3.6 + §3.7 (process).**
   Process changes don't require code; land them next.

4. **Defer §3.2 (foundation BlockAnchor amendment) and §3.4 (async race).**
   Both depend on §3.1's outcome.

5. **Re-plan R5.5 from the answers.** The current R5.5 plan
   (`docs/plans/2026-05-03-live-render-r5-5-holes.md`) and the v2-holes
   design (`docs/specs/2026-05-03-v2-holes-design.md`) are written around
   §3.1(a) status quo. If §3.1 changes, both documents need to be rewritten
   (or archived in favour of new ones). This is a re-plan, not a patch.

6. **Only after the above lands**, resume code work. The current
   implementation can stay on the `exploration/new-foundation` branch as a
   reference; the new approach should land alongside it (or replace it) per
   the §3.1 decision.

**Estimated time investment** for steps 1–5: 1–2 weeks of design work, no
implementation. This is comparable to the time spent on the failed dogfood
iteration; the difference is that it produces a stable architectural
foundation instead of more cycle guards.

## 7. Code state at time of writing

The branch `exploration/new-foundation` holds the R5.5 implementation in a
state where:

- All 10 live-render fast-tier tests pass.
- Mid-block split typing works (Bug B, D, E fixed).
- EOB-Enter creates a hole and the cursor lands on it (Bug A, C fixed).
- Idle-commit cursor delivery into the just-committed paragraph works (Bug C fixed).
- Anchor renumbering on qtPos=0 typing is invisible to the user (Bug D worked around).
- End-of-block typing in multi-paragraph docs no longer eats the next paragraph (Bug E fixed).
- Diagnostic `[dogfood]` logging is still wired in `LiveProxyBlockModel`, `LiveCursorState`, `LiveStructuralKeyHandler`, `LiveHoleLayer`, `LiveEditBinding`, and the QML delegates. Strip in the next changeset (whether that's the architectural-review-driven re-plan or a cleanup commit).
- The async commit window race (1.7) is **still present and unfixed**. Fast typing through an idle-commit can still scramble a few characters. Not user-reproduced in the most recent dogfood pass because typing-pattern was slow enough to commit-and-stop between characters.

The implementation is "usable for dogfood" in the narrow sense that
typing into split paragraphs and into newly-created paragraphs from
holes both work for slow typing. It is not "ready" by the spec's own
acceptance criteria (R5.5 dogfood script per §10.3), and the
architectural questions in §3 must be answered before claiming so.
