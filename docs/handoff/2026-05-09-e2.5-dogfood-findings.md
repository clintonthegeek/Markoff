## D1 — Ctrl+S does not save

**Observed:** Editing text and pressing Ctrl+S does not write the file. Title never gains `*`.

**Hypothesis:** `LiveView.qml`'s `Component.onCompleted` calls `root.Window.window` to register
actions, but the `Window.window` attached property may be `null` at `Component.onCompleted`
time when `LiveView` is a child of a not-yet-shown `ApplicationWindow`. If `w` is null, the
`w.addAction(...)` calls are all silently skipped and no shortcuts fire.

**Reproducer:** Add `console.log("window:", root.Window.window)` in `Component.onCompleted`
of `LiveView.qml` and observe whether it is null on launch.

**Fix direction:** Either (a) delay action registration to `Window.onActiveFocusItemChanged`
or use a `Connections { target: root.Window.window }` binding that fires when the window
becomes available, or (b) move action registration from `LiveView.qml` to `Main.qml` where
`ApplicationWindow` is the root and `window` is `self`.

## D2 — Multi-block selection: copy/cut affects only one block

**Observed:** Select multiple paragraphs with the mouse (cross-block selection). Ctrl+C /
Ctrl+X only operates on one block — the anchor block if selection is top-to-bottom, the
active block if selection is bottom-to-top.

**Root cause area:** `LiveClipboardController::copy()` / `cut()`. These methods retrieve
`selectionView()->anchorBlock()` and `selectionView()->activeBlock()`, but the iteration
of blocks in range may be using only one endpoint, or the selection anchor/active block
indices may be unreliable for cross-block selections.

**Fix direction:** Audit `LiveClipboardController::copy()` — confirm it calls
`iterateBlocks()` and collects all blocks between `min(anchorBlock, activeBlock)` and
`max(anchorBlock, activeBlock)` inclusive, trimming text at the anchor and active ends.
Similarly for `deleteSelection()` in `LiveSelectionView`.

## D3 — Arrow-key selection is totally inert for clipboard

**Observed:** Holding Shift and pressing ↓ moves the TextEdit cursor into adjacent blocks
and extends the visual selection within a delegate, but Ctrl+C / Ctrl+X have no effect —
nothing reaches the clipboard.

**Root cause:** QML `TextEdit` has its own internal selection model. When the user
navigates with Shift+arrow, `TextEdit.selectedText` is populated, but `LiveSelectionView`
(the C++ selection backing) is NOT updated. `LiveClipboardController` reads from
`LiveSelectionView`, not from the focused delegate's `TextEdit.selectedText`.

**Architectural gap:** Two separate selection subsystems:
- Mouse selection → `LiveSelectionView` (C++ authoritative)
- Keyboard selection in a delegate → `TextEdit.selectionStart/End` (QML-internal, not
  propagated to `LiveSelectionView`)

**Fix direction:** The delegate's `Keys.onPressed` handler (or `LiveStructuralKeyHandler`)
needs to sync `TextEdit.selectionStart / selectionEnd` back into `LiveSelectionView` after
each Shift+arrow keystroke. This requires determining the block row from the delegate and
calling `LiveSelectionView::begin()` / `extend()` with translated coordinates.

This is a moderate architectural task, not a one-liner.

## D4 — No right-click context menu visible

**Observed:** Right-clicking anywhere in the view shows nothing.

**Root cause:** Two compounding issues:
1. `LiveView.qml`'s `MouseArea` handles right-click but may not call `contextMenu.showForBlock()`.
2. The E2.5 spec §5 replaced the designed `QMenu`/Widget-bridge context menu with a QtQuick
   `Menu` (`LiveContextMenu.qml`). The original architectural decision (documented in
   `docs/specs/2026-04-29-live-render-design.md` §Widget-window bridge and
   `docs/plans/2026-04-29-live-render-walking-skeleton.md`) mandates a **native `QMenu`
   via the KDAB Widget-bridge pattern** for all context menus. This decision predates E2.5
   and was not overridden.

**Fix direction (correct approach — native QMenu):**
- Retire `LiveContextMenu.qml` (QtQuick `Menu`).
- Create `LiveContextMenuHandler.{h,cpp}` — a `QML_ELEMENT` `QObject` owning
  `std::unique_ptr<QMenu>` and populating it from `LiveActionController`'s QActions.
- Wire right-click in `LiveView.qml` to `contextMenuHandler.popup(globalPos)`.
- Reference: `docs/specs/2026-04-29-live-render-design.md` §Widget-window bridge,
  `docs/plans/2026-04-29-live-render-walking-skeleton.md` §LiveContextMenuHandler.

**Note:** the existing `tst_live_render_context_menu` tests the C++ side
(`canUndoForBlock`, `undoForBlock`) and is independent of the QML `Menu` vs `QMenu` choice
— it will not need to change.

## D5 — Doc-wide undo/redo absent; limited to active block

**Observed:** After editing block A and then block B, Ctrl+Z while in block B undoes only
block B's changes. Switching focus back to block A restores the ability to undo block A's
changes. There is no interleaved document-wide undo stack.

**Root cause:** `LiveActionController::undoAction` / `redoAction` call
`doc->undoD2()` / `doc->redoD2()`. These operate on the D2 per-block `UndoLog`, which is
keyed to the **last-edited block** in the document, not a chronological cross-block stack.

**Architectural note:** A true cross-block undo stack would require either:
- A wrapper that records edit operations (block ID + offset + content delta) in a shared
  `QUndoStack`, OR
- Using `UndoLog::Transaction` across block boundaries.

This is a **plan-level feature**, not a quick patch. Recommend deferring to a separate
E2.5.x bugfix phase or E2.6 scope brainstorm rather than fixing inline.

## D6 — Shift+↓ from block-start skips the anchor block

**Observed:** With the caret at column 0 of a `##` heading (just before the `#`), pressing
Shift+↓ moves the caret into the block below and then begins extending selection downward.
The heading block itself is not included in the selection.

**Root cause:** `LiveStructuralKeyHandler` or the cross-block Shift navigation logic
extends selection starting from the *destination* block, not from the anchor position.
The anchor (column 0 of the heading) is recorded but the first extend call sets the active
to the next block rather than recording the anchor-to-next-block-start range.

**Fix direction:** When `selectionView->anchorBlock()` is set and Shift+↓ is pressed,
the selection should span from the anchor position to the new active position, including
the anchor block's remaining text.

## D7 — Double-click does not select a word

**Observed:** Double-clicking a word in a delegate does nothing (cursor moves, no selection).

**Root cause:** The `MouseArea` in `LiveView.qml` (or per-delegate) intercepts mouse events
before `TextEdit` can process them as double-click word-select.

**Fix direction:** Allow `TextEdit` to handle double-click natively, or implement
word-boundary detection in the delegate's `onDoubleClicked` handler and call
`TextEdit.select(wordStart, wordEnd)`.

---

## D8 — Triple-click does not select a block/paragraph

**Observed:** Triple-clicking in a delegate does not select the full paragraph/block text.

**Root cause:** Same as D7 — `MouseArea` intercepts mouse events before `TextEdit` triple-
click behavior fires.

**Fix direction:** Implement triple-click handler in the delegate that calls
`selectionView.begin(row, 0)` + `selectionView.extend(row, text.length)` to select the
full block.

---

## D9 — Test app insufficient for empty-doc and save testing

**Observed:** The test app requires an existing file path argument. It cannot easily test:
- Typing into a freshly empty doc (no `--new` flag)
- Save roundtrip (Ctrl+S is broken per D1)

**Fix direction:** 
- Add an optional `--new` flag to `main.cpp` that starts with an empty document and a
  writable output path.
- Fix D1 (Ctrl+S) so save can be verified.
- Possibly add a `File` menu with Open/Save-As for basic file management.
