## If something surprises you

The plan was written by an agent who did not run the code. Reality may diverge. Examples:

- A test in the plan compiles but fails for a reason not anticipated in the plan. → Investigate root cause; if the test's expectation is wrong, update the test (and the spec if needed) and proceed. If the implementation is wrong, fix it.
- A Qt 6.8+ API behaves slightly differently than the plan assumed. → Adjust the plan's code in your task's commit; a small amendment is fine.
- An invariant in the foundation broke in a way the plan didn't see. → Stop, investigate, propose a small spec amendment in a new commit, then proceed.

In all cases: small fix-forward commits are preferred over re-running brainstorming. The plan amendment + a one-line commit message is the right granularity.

If the surprise is **large** (a whole task's premise turns out wrong, or a stakeholder veto surfaces), stop and escalate to the user with a clear summary. Do not silently re-design.
