# Markoff Code Audit — 2026-04-15

Code-first audit. Every observation below comes from reading source files
with no prior doc context. Docs are consulted separately in Part II.

---

## Part I: Code-Only Observations

### Architecture at a Glance

Markoff is a QGraphicsView-based markdown editor where each "block" (paragraph,
table, image) is an independent QGraphicsItem in a vertically-stacked scene.
The core class hierarchy:

```
Editor (QGraphicsView)
  └─ SelectionScene (QGraphicsScene)
       └─ SceneCoordinator (manages item list, reparse, serialization)
            ├─ MarkdownTextItem (editable text, QGraphicsObject + SelectableItem)
            │    ├─ TextControl (forked QWidgetTextControl)
            │    ├─ QTextDocument
            │    ├─ MarkdownHighlighter (QSyntaxHighlighter, AST-driven)
            │    ├─ MathTextObject (QTextObjectInterface)
            │    └─ CheckboxTextObject (QTextObjectInterface)
            ├─ TableBlockItem (read-only table, BlockItem)
            ├─ ImageBlockItem (read-only image, BlockItem)
            └─ StubBlockItem (test placeholder)
       └─ SelectionManager (cross-boundary mouse/keyboard selection)
  └─ FoldingModel (heading fold state)
  └─ FoldGutter (viewport-pinned fold arrows)
  └─ SearchBar (find/replace UI overlay)
  └─ LinkRenderer (typed link emission surface)
```

---

### THE GOOD

**1. Clean public API surface.**
Seven headers in `include/markoff/` — that's disciplined. The consumer sees
`Editor`, `Theme`, `EditorSettings`, `SearchBar`, `ResourceProvider`,
`LinkRenderer`, `FoldingTypes`. Internals stay in `src/`. Forward declarations
keep header coupling low. This is well done.

**2. SelectableItem is a good abstraction.**
The `SelectableItem` interface bridges text items and block items for unified
selection. Text items do hit-test/selection, block items do fully-selected.
The SelectionManager's state machine (None → WithinItem → CrossBoundary) is
clear and well-reasoned. The `ungrabMouse()` call in SelectionScene on mode
transition is a subtle but correct fix for Qt's implicit mouse grab.

**3. AST-driven highlighting, not regex.**
`MarkdownHighlighter` uses a pre-built span map from tree-sitter, not regex
patterns. This is fundamentally right — regex markdown highlighting is a
perpetual source of bugs. Spans carry semantic flags (bold, italic, heading,
math, wikilink, etc.) and the highlighter just applies formats. Clean
separation of concerns.

**4. FoldingModel is well-engineered.**
Pure data, no widgets. Heading paths as `QStringList` identity keys. Clean
reconcile logic that intersects fold state with new heading sets.
`isHiddenByFold` correctly checks ancestor prefixes. Bulk operations
(`foldAll`, `foldLevel`) emit a single signal. Serialize/restore is versioned.
The test coverage here is the best in the codebase.

**5. The TextControl fork is honest.**
The header and private struct openly declare it's forked from
`QWidgetTextControl`. The SPDX headers carry both the original Qt Company
copyright and GPL-3.0-or-later. This is the right way to handle a Qt internal
fork — the alternative (reimplementing from scratch) would be far worse.

**6. Inline math round-trip is careful.**
The U+FFFC substitution with `RawProperty` storing the original `$...$` form
means serialization always recovers the exact source. The strip → reparse →
re-substitute cycle in `SceneCoordinator::reparse()` keeps span offsets
aligned. `blockSignals(true)` during substitution prevents cascading
rehighlights.

---

### THE BAD

**7. Editor.cpp is a 1600-line god class.**
Editor owns scene creation, keyboard handling, context menu, auto-scroll,
search/replace, fold delegation, link emission, scroll position math, and
formatting actions. It touches nearly every internal type. Many of these
responsibilities could be extracted:

- Search/replace logic → SearchController or similar
- Formatting actions (toggleBold, insertTable, etc.) → FormattingCommands
- Scroll position visual-line math → ScrollMapper
- Link signal subscription → already half-extracted to LinkRenderer but the
  bridge logic lives in Editor

This isn't just aesthetics — when you add features (regex search, more
formatting, new block types), Editor.cpp is where all the churn lands.

**8. `goto` in MarkdownTextItem::keyPressEvent.**
Line 589: `goto cjk_done;`. This is in the CJK autocorrect logic. The code
works, but `goto` in a Qt event handler is jarring. A helper function or
early-return restructuring would be cleaner and safer against future edits
that add code between the goto and the label.

**9. EditorSettings is declared but never applied.**
`EditorSettings` has fields for `tabSize`, `lineNumbers`, `lineWrap`,
`highlightCurrentLine`, `highlightingEnabled`, `tripleClickSelectsLine`.
But `setEditorSettings()` in Editor.cpp just stores the struct — it doesn't
propagate any of these to the coordinator, text items, or highlighter.
This is dead API surface. Either wire it up or remove it.

**10. `goToLine()` only works within the focused text item.**
`Editor::goToLine()` moves the cursor N blocks forward within the focused
MarkdownTextItem. But with multiple text items in the scene, "line 50" might
be in a completely different item. The method doesn't walk across item
boundaries at all. This is functionally broken for multi-item documents.

**11. `selectAll()` delegates to the focused item only.**
`Editor::selectAll()` calls `ti->textControl()->selectAll()` which selects
within one QTextDocument. It doesn't use `SelectionManager` to select across
all items. Compare with the context menu's "Select All" which correctly routes
through `SelectionManager::handleKeyPress`. The public `selectAll()` method
is wrong.

**12. `cursorLine()` / `cursorColumn()` are item-local, not document-global.**
These return block number + 1 within the focused item's QTextDocument, not
the global document line. If the cursor is in the third text item, line 1 of
that item is not line 1 of the document. Any consumer expecting global
coordinates gets wrong values.

**13. `cut()` leaves orphaned block items.**
`Editor::cut()` iterates text items and calls `removeSelectedText()`, then
clears selection. But if a non-text BlockItem was fully selected, it's never
removed from the scene. After cut, the user's clipboard has the content, but
the table/image remains visible. This is a bug.

**14. MarkdownSplitter is a black box dependency.**
`SceneCoordinator::loadMarkdown` and `reparse()` both call
`MarkdownSplitter::split()` which lives in markoff-parser. The split logic
determines what becomes a text item vs. a table vs. an image. If the splitter
gets it wrong (e.g., doesn't recognize a GFM table variant), the coordinator
has no fallback — the block just becomes part of a text item. There's no
validation or error reporting on the split result.

**15. `reparse()` uses `QTimer::singleShot(0)` to clear `m_inReparse`.**
This means `m_inReparse` stays true during the entire current event loop
iteration after `reparse()` finishes. Any slot triggered synchronously by
`emit reparsed()` will see `m_inReparse == true`, which suppresses text
change handling. If a signal handler modifies text, that edit gets silently
swallowed. The intent is clear (prevent recursive reparse), but the
implementation is timing-sensitive.

### THE UGLY

**16. Span offset adjustment is fragile and duplicated.**
There are THREE places that adjust span offsets:

1. `MarkdownHighlighter::adjustSpanOffsets()` — called on every
   `contentsChange` signal, does approximate offset shifting.
2. `MarkdownTextItem::applyInlineSubstitutions()` — builds a shift table
   and adjusts all spans after replacing source with U+FFFC.
3. `SceneCoordinator::reparse()` — strips substitutions, reparses, gets
   new spans, re-substitutes.

These three systems maintain overlapping, potentially conflicting views of
"where things are" in the document. `adjustSpanOffsets` is explicitly called
"approximate" — it handles the common case but the overlap/deletion logic
(lines 452-467 of MarkdownHighlighter.cpp) has edge cases that are hard to
reason about. When `applyInlineSubstitutions` shifts spans, it uses its own
shift table that doesn't know about `adjustSpanOffsets`'s prior modifications.

This is the single most likely source of subtle highlighting bugs. If a user
types rapidly inside a math region near a heading, the span map can drift
from reality until the next full reparse (150ms timer).

**17. `ensureHeadingMap()` is expensive and runs often.**
Every call to `enclosingHeadingPath`, `headingAtBlock`,
`headingIndexForItem`, etc. calls `ensureHeadingMap()` which — when dirty —
does a FULL re-parse of the entire document via a fresh `TreeSitterParser`.
This is O(n) in document size on every fold state change. The heading map is
marked dirty on `foldStateChanged`, which fires on every fold/unfold. So
folding a single heading re-parses the entire document tree.

The comment says "input sizes are modest (hundreds of blocks)" but a 10,000-
line markdown file with 50 headings will feel this.

**18. The `dynamic_cast` pattern for item type dispatch.**
Throughout SceneCoordinator:
```cpp
auto *mti = dynamic_cast<MarkdownTextItem *>(m_items[itemIdx]);
```
This appears ~15 times. The items list stores `SelectableItem *`, which has
`isTextItem()` and `asGraphicsItem()`, but to get a MarkdownTextItem you need
a dynamic_cast. The type system should make this cheaper — `isTextItem()`
exists, so a `static_cast` after the check is safe and faster. Some callsites
do use `static_cast` after checking `isTextItem()`, others use `dynamic_cast`
without the check, creating inconsistency.

**19. `toMarkdown()` serialization makes separator assumptions.**
`SceneCoordinator::toMarkdown()` joins items with `\n` for text-text
transitions and `\n\n` for anything involving a block item. This
"1 newline between text items, 2 newlines around blocks" rule is baked in
rather than driven by the original parse. If the source had `\n\n\n` between
paragraphs, round-tripping normalizes it to `\n`. Over time, the document
drifts from its original whitespace.

**20. Search highlight walks the full item list THREE times per keystroke.**
When the user types in the search bar:
1. `highlightAllMatches()` walks all items, finding and highlighting matches.
2. Inside that same function, it does a closest-match scan.
3. `updateMatchCount()` is also called on findNext/findPrev, which walks
   all items AGAIN to recompute the current index.

For a large document with 100 text items, this is O(n*m) per keystroke
(n items, m matches per item).

**21. The TextControl fork is ~2000 lines of Qt internals with no test coverage.**
`TextControl.cpp` and `TextControl_p.h` together reimplement a significant
chunk of `QWidgetTextControl`. None of the 15 test executables directly test
TextControl behavior. Tests exercise it indirectly through MarkdownTextItem,
but there are no tests for:
- Cursor movement edge cases
- Input method handling
- Drag and drop
- Link activation/hover
- Preedit composition
- Triple-click behavior

If any behavior diverges from Qt's original (and it will, over time, as Qt
evolves and the fork doesn't get upstream fixes), there's no regression net.

**22. Theme hardcodes QOwnNotes schema format.**
`Theme::fromSchemeFile()` reads a QSettings-based format with keys like
`ForegroundColorEnabled_0`, `Bold_4`, `FontSizeAdaption_12`. These index
numbers and key patterns are QOwnNotes-specific. The code imports
QOwnNotes color schemes but doesn't document this anywhere in the public API.
A new user trying to create a theme would have to reverse-engineer the
expected format.

**23. No accessibility considerations visible anywhere.**
None of the QGraphicsItems set accessibility properties. MarkdownTextItem
doesn't expose its text content to QAccessibleInterface. Screen readers will
see a QGraphicsView with opaque items. There's no high-contrast mode support,
no keyboard-only navigation testing, no ARIA-equivalent metadata on the
custom text objects.

**24. `setFontSize()` mutates the theme.**
`Editor::setFontSize()` modifies `m_theme.textFont` directly:
```cpp
m_theme.textFont.setPointSize(pointSize);
```
So after calling `setFontSize(18)`, `editor->theme()` returns a theme whose
textFont is 18pt, regardless of what was set via `setTheme()`. The theme and
font size are coupled in a surprising way. If the host app does
`setTheme(dark)` then `setFontSize(18)`, the theme's font is now 18pt. If it
then does `setTheme(dark)` again (to "reset"), the font jumps back to 14pt.

**25. FoldingTypes.h forward-declares HeadingInfo but doesn't include it.**
Line 10: `struct HeadingInfo; // fwd decl from markoff-parser`
But `computeHeadingPaths` takes `const QList<HeadingInfo> &headings`. The
consuming TU must have already included the markoff-parser header that defines
`HeadingInfo`, or compilation fails. This is a hidden include-order
dependency in a PUBLIC header.

### Questions from a Fresh Reader

1. **Why is TextControl a fork rather than using QWidgetTextControl directly?**
   What customizations are needed that the Qt original doesn't provide?
   The header says "Forked from Qt's QWidgetTextControl" but doesn't say WHY.

2. **What happens when you paste rich text?**
   TextControlPrivate has `acceptRichText = false` but there's no visible
   plain-text coercion in the paste path. Does Qt handle this?

3. **Can two MarkdownTextItems be merged?**
   If the user deletes at the boundary between two text items, does the
   backspace cause a merge? The `cursorAtBoundary` signal exists for
   navigation, but there's no merge logic visible.

4. **What happens to undo history when reparse restructures items?**
   If typing causes a structural reparse (block count changes), all items
   are `clearItems()` + recreated. The undo history of every QTextDocument
   is destroyed. Is this intentional?

5. **Why is the reparse timer 150ms?**
   Is this tuned to feel responsive, or is it an artifact? 150ms is noticeable
   for fast typists. Some editors use 0ms (microtask) for incremental updates
   and only defer full structural reparses.

6. **Where does the `Document` class come from?**
   `Editor::onDocumentReparsed()` calls `Document::fromMarkdown()`, which
   returns headings, links, tags, word count. But `m_document` is a
   `std::unique_ptr<Document>` that's only ever read via `document()`. It
   seems like an expensive re-parse just to emit metadata signals. Does
   `Document::fromMarkdown` share the parser with `SceneCoordinator`?

7. **What is `MarkoffBlockData` for?**
   It has `DisplayMode`, `renderedHeight`, `renderedCache`, `cacheValid`. But
   I can't find any code that creates or reads `MarkoffBlockData` instances.
   Is this dead code?

8. **Why doesn't `ImageBlockItem` respond to width changes?**
   `SceneCoordinator::setItemWidth()` calls `setTextWidth()` for text items
   but explicitly comments "StubBlockItems have fixed width." Images and
   tables are created with a `maxWidth` at construction time, but nothing
   updates them when the viewport resizes.

9. **What prevents typing in read-only mode from reaching block items?**
   `setReadOnly()` sets `TextBrowserInteraction` on text items, but
   `TableBlockItem` and `ImageBlockItem` have no read-only concept. What if
   a future block item is editable?

10. **Where is the completion popup?**
    `detectCompletionTriggers` emits `wikiLinkTrigger` and `tagTrigger`, but
    there's no popup implementation in markoff. Is this expected to be handled
    entirely by the host app?

## Part II: Code vs. Docs Comparison

### architecture.md — Mostly Accurate, Some Drift

The architecture doc is well-written and mostly matches the code. Key
discrepancies:

**Stale header count.** The architecture says "four headers in
`include/markoff/`" listing Editor.h, Theme.h, EditorSettings.h,
ResourceProvider.h. The actual public include directory has SEVEN headers:
those four plus SearchBar.h, LinkRenderer.h, and FoldingTypes.h. These
were added by later feature work (find/replace, Cluster J link emission,
heading folding) but the architecture doc was never updated.

**ImageBlockItem exists but architecture says "Planned."** The architecture's
"Planned Block Item Types" table lists ImageItem as future work. But
`ImageBlockItem` is fully implemented in `src/ImageBlockItem.h/cpp` and
wired into `SceneCoordinator::loadMarkdown()`. The architecture doc is
out of date.

**No mention of CheckboxTextObject.** The architecture discusses
MathTextObject at length but doesn't mention the checkbox substitution
system at all, even though it shares the same U+FFFC mechanism.

**"DocumentBuilder — planned for removal."** The architecture says the
MD4C-based DocumentBuilder is planned for removal once Renderer migrates
to tree-sitter. This is still true — it's in the sibling markoff-parser
library, not markoff itself — but the architecture doesn't clarify this
separation.

**ReadingView is documented but not in markoff.** The public API spec
promises `ReadingView.h` and `RenderSettings.h` as public headers, and
the architecture references a Renderer. None of these live in
`libs/markoff/`. They appear to live elsewhere in the Corbomite tree
(likely the parent app layer). The markoff library scope is editor-only.

### Heading Folding Spec — Fully Implemented, Status Header Stale

The spec file `2026-04-15-heading-folding-design.md` says:
> Status: Design approved 2026-04-15. Awaiting implementation plan.

This is wrong. The implementation plan EXISTS at
`docs/plans/2026-04-15-heading-folding.md` and ALL of the following are
fully implemented and tested:

- `FoldingModel` with path-based fold state — **done, 174 lines**
- `FoldGutter` with `GutterColumn` interface — **done**
- `FoldArrowColumn` with Ctrl+Click for level fold — **done**
- `SceneCoordinator::applyFoldVisibility()` — **done, block-level**
- Auto-unfold on `scrollToHeading` and `findText` — **done**
- `serializeFoldState` / `restoreFoldState` JSON — **done, versioned**
- All 5 planned test files — **done, 61 test functions total**

The spec should have its status updated to "IMPLEMENTED."

### Public API Spec — Implemented But Scope Narrower Than Promised

The spec (`2026-04-02-markoff-public-api-design.md`) promises 7 public
headers. In practice, the headers are DIFFERENT from what was specified:

| Spec promised | Actually shipped |
|---|---|
| Editor.h | Editor.h |
| Theme.h | Theme.h |
| EditorSettings.h | EditorSettings.h |
| ResourceProvider.h | ResourceProvider.h |
| Document.h | (lives in markoff-parser, not markoff) |
| ReadingView.h | (not in markoff) |
| RenderSettings.h | (not in markoff) |
| — | SearchBar.h (new) |
| — | LinkRenderer.h (new) |
| — | FoldingTypes.h (new) |

Three headers the spec promised are in sibling libraries or the host app.
Three headers exist that the spec didn't predict. The spec's "7 headers"
claim is numerically correct but the LIST is wrong.

### EditorSettings — Spec Matches Code, But Code is Dead

The spec defines `EditorSettings` with 5 fields. The code has 6 fields
(adds `tripleClickSelectsLine`). But as noted in the code audit above,
`setEditorSettings()` stores the struct and NOTHING reads it. The spec
describes each field's intended effect, but the code never implements
those effects. The spec is aspirational; the code is a dead struct.

### Find/Replace Spec — Fully Implemented, Matches Code Well

The find/replace spec matches the implementation closely. The SearchBar
widget exists with both find and replace rows, keyboard shortcuts work
(Ctrl+F, Ctrl+H, Escape, F3), match counting with "3 of 17" display is
implemented, and the 65536 highlight cap is present. The spec's "Deferred
features" (regex, whole-word, search-in-selection) are correctly absent
from the code.

### TODO.md — Partially Stale

TODO.md lists several items under "Editor API gaps" that have been
resolved:

- "Links are not clickable/followable" — This IS now implemented via
  the LinkRenderer + Cluster J phase 3 wiring. The TODO entry references
  `Editor.cpp` line numbers that no longer match. The wikilink href
  annotation and TextControl bridge are both working.

- "In-editor image rendering" is listed as blocked:spec, but
  `ImageBlockItem` exists and is wired into the splitter pipeline. The
  TODO should either be removed or updated to note what's still missing
  (perhaps lazy loading, resize handles, etc.).

Other TODO items are still accurate:
- Editable tables (still read-only)
- Math cursor reveal complexity (still ~300 lines)
- Incremental tree-sitter parsing (still full reparse)
- Accessibility (still nothing)

### Cross-Cutting: "Obsidian grammar additions" are Partially Done

TODO.md says `==highlight==` and `%%comment%%` need grammar additions.
But the vendored grammar ALREADY supports these (`highlight` and
`obsidian_comment` nodes are mentioned in the architecture doc itself).
The remaining items (`![[embed]]`, `^block-id`, callout blocks) are
genuinely unimplemented.

## Part III: Top 10 Actionable Findings

Ranked by impact (bugs first, then architectural debt, then polish):

1. **`selectAll()` is broken** — delegates to focused item only, should use
   SelectionManager. Public API contract violated.

2. **`cut()` doesn't remove block items** — fully-selected tables/images
   survive cut. Data loss prevented (clipboard is correct) but visual state
   is wrong.

3. **`goToLine()` is item-local** — navigates within one QTextDocument,
   not the global document. Off by potentially hundreds of lines for
   multi-item documents.

4. **`cursorLine()` / `cursorColumn()` return item-local values** —
   consumers expecting global coordinates get wrong numbers.

5. **EditorSettings is dead API surface** — 6 fields, zero wired effects.
   Either implement or remove to avoid misleading consumers.

6. **`FoldingTypes.h` has hidden include-order dependency** — forward-
   declares `HeadingInfo` but public functions take it by reference.
   Consumer must include the parser header first.

7. **Span offset tracking is triply-redundant** — three systems maintain
   overlapping offset state. Most likely source of subtle rendering bugs
   under rapid typing.

8. **`ensureHeadingMap()` does a full tree-sitter reparse** — fires on every
   fold state change. O(n) in document size for a UI click.

9. **Stale documentation** — architecture.md, TODO.md, and the folding spec
   all have outdated claims. Consumers reading docs will form wrong mental
   models.

10. **Zero accessibility** — no QAccessibleInterface, no keyboard navigation
    testing, no screen reader support. This is a legal/ethical concern for a
    text editor, not just a polish item.
